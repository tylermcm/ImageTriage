# Cascade logic and evidence audit — 20 October 2026

Reviewed ImageTriage `main` at `8fb27f4d2c59da426eda2664452584a5c8c6bf9f`. This is an audit, with no changes to cascade behaviour. Findings come from the checked-out implementation, tests, spike scripts and saved JSON, not from the brief's interpretation. Original library photos, spike feature NPZs, score databases and keeper-labelled burst manifests are not present in this checkout; I did not rerun the original image/model experiments.

**Conclusion:** the core generally implements the stated procedural rules correctly. Passing those rules is not evidence that a group contains interchangeable photos or that a flag identifies an unwanted frame. The current thresholds are provisional heuristics, with useful owner feedback but no independent estimate of library-wide keeper recall or false stack merges. There are also concrete protection/explanation defects and a deliberately nonstandard clustering algorithm.

## Implementation findings

1. **Winner protection retains defect flags.** `cascade/task.py:326-335` restores a protected outcome to `final` but copies `outcome.flags`. `export.py:112` writes those flags to `triggered_tags`. I reproduced a protected singleton with `blink=True`: exported role `final`, summary “Kept: you already marked this frame as a winner,” but `triggered_tags=blink`. A protected frame already having role `final` is not rewritten at all, so it can retain a `blown_out` flag and the ordinary cleanup summary. Protection prevents the adverse role, but does not satisfy the literal promise “never flagged.” It also leaves the original stack position unchanged; it does not recompute ranking or grouping. This is a metadata/contract defect, not proof that the app hides a protected winner. Protection only covers readable frames with outcomes and paths supplied by the caller; `ai_run_controller.py:1111` supplies current winner annotations, not every historical keeper source used by the spike.

2. **The all-flagged explanation can be false.** `pipeline.py:51` restores all members whenever none is unflagged, even if they have different problems. For two identical-hash frames, A sharpness 100 with blink, B sharpness 1 without blink, A has `blink`, B has `soft`; both re-enter duplicate collapse. With equal extremes A becomes the final representative, mapped to `flagged`, and B becomes `duplicate`. `folder.py:198` says every frame has “the same problem,” which is untrue. The fallback only prevents pass 1 from assigning `REJECTED`; it does not preserve every frame as a first-choice result through later passes. This distinction matters when interpreting recall.

3. **`complete_linkage` is first-fit diameter-bounded clustering, rather than conventional agglomerative complete linkage.** `stacking.py:29-43` merges the first pair whose maximum cross-distance is at most T, not the pair with the smallest maximum distance. The diameter bound is correct and it prevents ordinary single-linkage chaining. But it changes which groups form. Example distances AB=8, AC=6, BC=10 at T=8: input A,B,C yields AB/C; A,C,B yields AC/B. Conventional closest-pair linkage merges AC first. Valid synthetic hash inputs are A=0, B=255, C=3843. This choice is documented in the function and copied from the spike, so it is not an accidental deviation from that script. It is a naming/algorithm expectation issue; changing it would change established outputs and needs a fresh review.

   I compared the current clusters with a closest-pair implementation, using the same alive frames, threshold 8, and index-order tie breaking. Four saved stacks differ: marked b15, b29, b30 and b32. For example b15 changes from `{0,1}/{2,5}/{3}` to `{0,1}/{2}/{3,5}`. Neither partition has independent human interchangeability labels.

4. **There are misleading exposure claims.** The representative minimizes the fraction of very dark or very bright *luma* pixels. That does not measure even illumination, subject exposure, RAW headroom or sharpness. With equal extremes it simply chooses the earliest frame, yet `folder.py:212` calls the chosen frame “better exposed.” A colour channel can be saturated while luma is not extreme: e.g. bright red can have high `clipped` but low bright-luma `extremes`.

5. **Some surprising outcomes are intentional rules, not coding mistakes.** All-blown stacks, including singletons, get `NO_PICK` before the all-flagged fallback. In a mixed stack, `blown_out` alone does not reject. With identical hashes, clipped fractions .45/.39 and extremes .01/.02, the .45 frame is the representative and the .39 frame is a duplicate: the relative clipping threshold is .78, so neither is relatively clipped. The .45 frame remains final with `blown_out`. A uniformly poor-sharpness stack also escapes the relative soft rule; zero against zero is not soft. These behaviours need product judgment, not an off-by-one fix.

6. **The numeric boundaries match the description.** Burst gap includes 5 seconds and excludes negative time differences; burst hash distance includes 20. Stacks split at >=18; duplicate diameter includes 8. Soft and relative clipping use strict comparisons; blown-out and blink use inclusive comparisons. Missing timestamps make singletons; unreadable/bracket frames interrupt bursts; soft/clipped do not apply to singletons. Duplicate keys within a burst raise `ValueError`. Every valid core frame gets a decision. No arithmetic or indexing defect was found on the extractor's ordinary finite inputs.

   The pure API is not defensive against arbitrary inputs: empty `flag_stack` raises at max/min; NaN features/scores, out-of-range fractions, negative keep counts and incomplete scorer mappings are not validated. A missing score raises `KeyError`; NaN ordering can be input-order dependent. These are robustness limits, not observed failures of the supplied extractor. `run_folder` also assumes unique paths and feature keys matching paths.

## When people will disagree, and how likely that is

| Operation | Trigger and consequence | What can be said about frequency |
|---|---|---|
| Stack split: false merge | Gradual pan/zoom/pose changes with every adjacent hash jump <18 keep one stack, however far apart its ends become. A background-dominated hash can ignore a new expression or small subject. Whole-stack sharpness/clipping then compares unlike frames. | Structural drift occurs in 8 of the fixture's 122 stacks: b10, b12, b14, b15, b30, b33, b44 and u23 have hash diameter >=18 (maximum 32). That is not a measured human false-merge rate. |
| Stack split: false split | Camera movement, crop/orientation, lighting or subject motion makes adjacent distance >=18 even though the person regards the frames as one choice. Folder segmentation already splits distances >20 or gaps >5 seconds. | Unmeasured. The reviewed u44 motivated 18 after the fact; it does not establish specificity or sensitivity. Within a folder burst, only adjacent distances 18–20 exercise the stack splitter. |
| Folder grouping | Same-folder, close-time frames from different cameras/photographers can join: `FolderFrame` carries no stream/camera identity. Missing or coarse EXIF times change groups and tie order. | Conditional on mixed streams and metadata quality; no prevalence estimate. The spike builders used a stream check, unlike this folder API. |
| Soft flag | Off-centre subject; intentional shallow depth of field; zoom/reframing; textured background; noise/sharpening makes one sibling's central Laplacian unusually high. A technically desirable frame falls below .4 of that maximum. | Plausible, especially after a false stack merge. No calibrated rate. Conversely, equally blurred frames and fine blur lost at 1280 px can be missed. |
| Clipping / no pick | Snow, white backgrounds, specular reflections, high-key images or saturated colours exceed JPEG channel thresholds although the subject is good. Camera rendering clips recoverable RAW data. An unusually dark sibling sets an inappropriate minimum. | Genre-dependent and unmeasured. Night/astro/long exposures remain outside demonstrated coverage. The .40 all-blown rule adds a sharp discontinuity: every member crossing .40 changes the whole stack to no-pick. |
| Blink | Closed eyes can be intentional laughter/squinting; another prominent person may not be the subject. Small faces are excluded; detector misses are treated as no blink. A wink with scores 1 and 0 averages .5 and is missed. | Later real validation has only 68 prominent-face frames out of 433, with two threshold hits and an observed .59 eyes-shut miss. No held-out confusion matrix supports a library-wide false-flag rate. |
| Duplicate collapse | Similar low-frequency layout but different eyes, expression, gesture, subject detail or focal sharpness. All pair distances <=8 does not imply photographic interchangeability. Lowest extremes can favour a blurred, flatter or less preferred frame. | Grouping is common (222/433 fixture frames are assigned duplicate), but harmful collapse is not labelled. Four fixture stacks demonstrate the first-fit/closest-pair distinction. Repeated equal-hash frames are the clearest risk for details pHash cannot see. |

No defensible percentage likelihood can be attached to the human errors above from these data. The observed structural counts identify exposure to a failure mode, not its human cost. Conversely, threshold noise, low-detail/flat images and exact ties deserve explicit tests rather than assumptions that a 63-bit hash uniquely describes a photograph.

## What the evidence actually supports

**The 87% figure has the wrong denominator in the brief.** `cascade_burst_spike.py` filters to `len(frames)>=3` before every configuration. There are 46 such bursts among the 63 marked cases (17 are pairs). The reported .870 survival and .587 after collapse are consistent with 40/46 and 27/46, respectively, not an evaluation over all 63. The plan's detailed experiment says 46; its opening shorthand obscures this. The quoted bootstrap interval is resampling bursts from a narrow collection, not uncertainty across a photo library.

**It is also a different pipeline.** That experiment used a 2% clipping floor, burst-level comparisons, older blink labels, distance-4 collapse and a different representative/ranking path. Current code uses 10%, stack-first comparisons, distance 8, even-extremes representatives and a MediaPipe blink worker. The old loss rate is a warning about the approach, not the current pass-1 recall. Raising a floor can reduce one kind of flag on fixed groups, but regrouping and changing blink inputs prevent carrying the headline rate forward.

**Round-2 cluster survival is not keeper recall or proof of distinct-moment preservation.** `cascade_burst_spike2.py` selects only the 12 or 9 bursts having at least three clusters *before pass 1*. Its removal and survival figures are computed on those subsets. At threshold 8 the .833 is 10/12; at 12 the .889 is 8/9. The clusters used as the target are defined by the same algorithm under evaluation. “Every cluster kept” when keeping every representative is true by construction, not independent evidence that no meaningful moment was lost. The stack-sheet script later selects on surviving cluster count in the pick's stack, so those denominators change again. These numbers cannot be pooled as repetitions of one metric.

**44/45 agreement is encouraging product feedback, not independent validation of the final thresholds.** Split-at-18, the clipping floor and all-blown handling were adjusted using that review. The same album cannot then establish their generalization. Agreement about an output sheet is not an annotation of every boundary, collapsed alternative or unseen flagged keeper. The sample is also restricted to 3–10-frame bursts passing the prefilter. The known keeper set spans China '26 and China 8-26; the unmarked set is Engagement Trip: two reviewed collections, but three album names in the scripts.

**The golden test is valuable regression coverage, not a human oracle.** It replays 108 bursts / 433 precomputed feature rows against decisions exported from `cascade_stack_sheet.py`. It does not run extraction, folder segmentation, current blink inference, winner protection or live rankers. It contains neither keeper indices nor timestamps nor independently judged stack boundaries, so current exact keeper recall and folder merge rate cannot be recovered from it alone. Its blink values are Facet database `is_blink`, not the current worker's scores: it contains 14 blink-positive rows, whereas the later MediaPipe notes report two threshold hits on these sets.

Production feature parity also needs qualification: spike images were resized with Lanczos and re-encoded, its Laplacian used OpenCV on the cropped centre, and production uses JPEG draft/BOX and its own Laplacian crop. Later worker tests establish excellent MANIQA score parity and Q-ReAlign parity on identical images, but Q-ReAlign versus the old stored RAW-render scores correlates only .59. That proves input rendering matters; it does not validate the final selection results using the new rendering.

My replay of the fixture with defaults and no rankers yields 36 rejected, 222 duplicate, 164 final and 11 no-pick frames. With the fixture's stored ranker scores: 36 rejected, 222 duplicate, 150 final, 11 no-pick, 11 cut by ranking and 3 cut by MANIQA. These are output counts, not accuracy estimates.

Consequently, 18, .4, 2x/.10, .40, 8 and the 3/2 keep counts are reasonable candidates for review, not demonstrated optima or safety limits. Chance-level top-1 results do not logically prove top-2 ranking is useless, but the directly measured top-2 results also failed the experiment's criterion. They do not support calling rank 1 an `OBVIOUS_WINNER`. The plan's opening “collapse removed/rankers retired” policy also conflicts with its later stack-first description and the actual code; that documentation needs an explicit current decision.

## A sound next measurement

**Keeper recall:** rebuild the positive inventory from winner copies, Accepted XMP and edited exports, resolve each to its original exposure using album/stream/file identity and metadata, manually verify ambiguous matches, and deduplicate RAW/JPEG pairs and repeated exports. The existing album-plus-basename heuristic is not sufficiently reliable as ground truth. Include all known positives, including singleton, multi-keeper, long-burst, missing-EXIF, unreadable, bracket and night/astro cases; do not condition on exactly one keeper or on the model's number of surviving groups. Unmarked photos are not negatives.

Run the actual current extraction and folder context with fixed settings. Compute the raw flags in a shadow evaluation before winner protection, otherwise annotation-based protection makes recall trivially perfect for the very positives being tested. For each rule report the number of eligible keepers, number flagged and exact list/reasons of failures; also report the union of rejecting flags, actual pass-1 rejection after fallback, no-pick separately, and final exact-frame survival after collapse/ranking. Report unreadable/skipped/missing-metadata coverage instead of treating it as success. Measure human-labelled interchangeable-alternative retention separately from exact-frame retention.

Keep tuning albums separate from evaluation albums/events; freeze thresholds first. Report frame-weighted and album/genre-specific results, with uncertainty respecting event clustering. Around 200 known keepers is useful for discovering failures, not proving 99.5% safety: even zero misses among 200 independent examples gives only about a 98.51% one-sided 95% lower bound. Zero misses need at least 598 independent examples to put that bound above 99.5%; dependence and simultaneous per-rule claims need more care. High recall per rule also does not imply equally high recall for their union. Add targeted real defect labels to assess useful flag precision; positives alone cannot tell whether the rules remove meaningful junk.

**False stack merges:** define the human question first: “should these frames be compared as alternatives in one stack?” is broader than “are these interchangeable duplicates?” Obtain both labels where collapse is evaluated. Reuse the 256 labelled pairs and the 29 ten-frame strips / 261 step labels as initial material, join them back to originals/features, and rerun the *current* hash and segmentation. The saved round-2 metadata lacks the current feature/time arrays, so labels alone are insufficient. Deriving strip partitions from adjacent labels assumes contiguous human groups; annotate full groups if returning to earlier poses is allowed.

The earlier work already contains false-merge counts for a different average-linkage/learned-feature grouping experiment. It is inaccurate to say the repository has no false-merge evidence at all; it has no validated false-merge rate for this stack splitter. A quick diagnostic on the saved round-1 pair metadata finds one human “different” pair, id 22, among 125 pairs passing 0<=gap<=5 and old-hash distance <18 (that pair has distance 10, gap 2.52 seconds). This is evidence against treating a small pHash gap as sufficient. It is not the current pipeline's error rate: hashes came from a different preprocessing path and pairs were sampled in unequal, model-selected strata.

Sample complete runs across held-out albums, with extra coverage near 8 and 18, gradual drift, illumination changes and multi-camera folders. Review all members in capture order without showing model decisions first. Include enough surrounding frames to avoid cutting a proposed stack at the edge of a ten-frame strip. Report (a) human boundaries missed, (b) predicted stacks spanning multiple human groups, (c) different-group frame pairs co-stacked, and (d) false splits / same-group pair retention. Test duplicate false merges separately. Give numerators/denominators, event-aware intervals, and population weights for deliberately oversampled strata; the round-1 sampling counts can help only for their defined sampling population. Compare threshold sweeps and simple baselines on tuning data, then confirm the frozen choice on untouched albums. Scene-retrieval labels are a different task and should not substitute for burst-stack labels.

- **Fixed (`e744cfe`):** winner protection now clears the flags it overrules (a protected pick stays the pick); the all-flagged explanation says "every frame in this stack was flagged, so none could be set aside"; the duplicate explanation names the frame kept without calling it better exposed; `docs/ai_v5_plan.md` states that the 87% figure is 40 of the 46 bursts with three or more frames, on an older pipeline.
- **Options added, defaults unchanged (`218425c`):** `CascadeSettings.linkage` ("first_fit" today, "closest" conventional), `max_stack_span`, `split_focal_ratio`, `split_face_ratio` and `all_flagged_skips_collapse`; `FrameFeatures.focal_mm` (filled from the EXIF focal length, which is the plain value, not the 35 mm equivalent, because that is all the metadata reader carries) and `face_area` (filled only by the audit script's `--faces-json`).
  On the golden fixture (108 bursts, 122 stacks): `closest` changes 2 bursts, `max_stack_span=18` splits 10 extra stacks and changes 8 bursts, `=24` changes 6, `all_flagged_skips_collapse` changes 2. These are output differences, not accuracy: no human labels exist for the changed bursts.
- **Measurement tooling (`64b4737`, plus RAW/JPEG companion merging):** `scripts/ai_v5/pass1_audit.py` with the pure logic in `image_triage/cascade/audit.py`. Per rule keeper recall with an exact one-sided 95% lower bound and the number of keepers still needed (598 with zero misses for 99.5%), the union, the all-flagged fallback, no-pick and final exact-frame survival, coverage (unreadable, missing time, brackets, unmatched keepers), threshold and option sweeps, per-folder results, stack hash diameter, and a blind review page (`--review-pairs`) of pairs that are in one stack although focal length or face size or drift disagrees with the hash. It runs `run_folder` without the winner-protection step. A RAW and its same-named JPEG in one folder are one frame, as in the app.
  **Workflow: run first, choose keepers afterwards, blind to the run** (a keepers list made before, or from the app with flags showing, biases the recall; the order below is how culling is really used):
  1. `python scripts/ai_v5/pass1_audit.py --folders D:\Photos\trip1 D:\Photos\trip2 --out run1 --cache audit_cache.json --pick-sheet --review-pairs 60` reads the images once and writes `run1/frozen.json` (every frame's hash, measures, time and focal length), `run1/report.md` (flag rates and stack diagnostics, no recall yet) and `run1/pick/index.html`.
  2. Open `run1/pick/index.html`, click the frames you would keep on each page (frames in capture order; no flags, stacks or dimming are shown, nothing comes from the run) and press "download keepers" (a JSON list of paths per page).
  3. `python scripts/ai_v5/pass1_audit.py --from-frozen run1/frozen.json --keepers keepers_01_01.json keepers_01_02.json --out run1_eval --sweep-json sweep.json` judges the same frames against your picks with **no image read**, so thresholds and the new options can be swept and re-swept afterwards. Optional: `--blink-scores`, `--faces-json`, `--settings-json`, `--full-grid`.
  Keepers chosen from a folder that was already culled (winner copies, Accepted marks) still work as `--keepers` input but carry the selection bias described above.
  Not yet exercised on real RAW folders or real keeper lists. Blink recall is only measured when a `--blink-scores` file (path to score) is supplied.
